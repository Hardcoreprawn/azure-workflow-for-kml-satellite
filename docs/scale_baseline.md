# Scale Baseline: 200+ AOI KML Processing

**Issue**: [#437 — End-to-end validation: prove 200+ AOI KMZ processing at scale](https://github.com/Hardcoreprawn/azure-workflow-for-kml-satellite/issues/437)
**Stage**: Stage 2 exit criterion

## Summary

This document records the repeatable methodology and baseline metrics used to
prove Stage 2's claim: _"200+ concurrent AOIs process reliably without OOM or
timeout"_.

## Test location

`tests/test_monster_aoi_scale.py`

```bash
# Run the full scale gate (no external dependencies required)
make check

# Or directly:
uv run pytest tests/test_monster_aoi_scale.py -v -m "not integration" -s
```

## Fixture

`tests/fixtures/monster_200.kml` — generated by `scripts/generate_monster_kml.py`:

```bash
python scripts/generate_monster_kml.py --count 200 --out tests/fixtures/monster_200.kml
```

The KML places 200 distinct 2×2 km square polygons in a 15×15 grid starting at
`(-60.0, -10.0)` with 0.05-degree spacing (approximately 5 km), covering roughly
0.75° × 0.75° (≈83 km × 83 km) of the Brazilian Amazon.

## Assertions

### Phase 1 — Parse-level (no external dependencies)

| Assertion | Expected |
|-----------|----------|
| Feature count | exactly 200 |
| All AOIs have `area_ha > 0` | no degenerate polygons |
| All AOI bboxes are distinct | no coordinate collisions |
| All AOIs have `perimeter_km > 0` | valid ring geometry |
| All Placemarks have non-empty names | no anonymous features |
| Parse wall-clock | < 15 s |

### Phase 2 — Enrichment fan-out (mocked I/O)

| Assertion | Expected |
|-----------|----------|
| `per_aoi_enrichment` length | exactly 200 |
| Dropped AOIs (None or `{}` result) | 0 |
| AOIs with `error` key | 0 |
| Total fan-out wall-clock | < 60 s |
| Per-AOI p99 (stub overhead only) | < 1 000 ms |
| `enrichment_duration_seconds` present | yes |

## Baseline metrics (stub run — no network I/O)

These figures represent the overhead of the fan-out mechanism itself (thread
scheduling, result collection) with all network calls mocked to no-ops.  They
establish a floor below which the real implementation should not fall.

| Metric | Value |
|--------|-------|
| Wall-clock (200 AOIs, mocked) | ~16 ms |
| Per-AOI p50 | < 0.1 ms |
| Per-AOI p95 | < 0.1 ms |
| Per-AOI p99 | < 0.1 ms |
| Mean per-AOI | < 0.1 ms |

> **Note**: The p50/p95/p99 timings printed during `make check -s` reflect only
> the stub overhead.  Real production runs (live STAC, NDVI, weather APIs) will
> be orders of magnitude slower per-AOI but still bounded by the
> `DEFAULT_ENRICHMENT_CONCURRENCY` thread cap.

## Regression gate

`tests/test_monster_aoi_scale.py` is part of the standard `make check` suite
(no `integration` mark on the parse and fan-out tests).  Every PR that touches
the parser, geo, or enrichment code will exercise these assertions automatically.

### Re-running against a live environment

```bash
make dev-all        # Azurite + local Functions host
make test-int-live  # live-stack integration tier
```

The integration test class (`TestPipelineSmokeMonster`) validates connectivity
to Azurite and the Functions host. Individual tests skip when dependencies are
absent, but the tier runner fails an all-skipped run so missing infrastructure
cannot produce a green integration gate.

## Methodology notes

- The fan-out is parallelised via `ThreadPoolExecutor` with a cap of
  `DEFAULT_ENRICHMENT_CONCURRENCY` workers (see `treesight/constants.py`).
- Each AOI's enrichment is isolated inside `_enrich_safe`, which catches and
  records exceptions rather than letting them abort sibling AOIs.
- Multi-region detection (`_is_multi_region`) is bypassed in the monster fixture
  because all 200 polygons are within the same 83 km × 83 km bounding box.
- Memory: the test runs without any in-process limit.  On CI (GitHub-hosted
  Ubuntu runner, 7 GiB RAM) the test completes within the standard timeout with
  no OOM signal.
